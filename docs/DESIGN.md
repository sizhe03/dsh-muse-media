# dsh-muse-media 设计与实现说明

## 一句话

插件通过 CDP 驱动本机 Chrome 操作 muse.ai 网页，把「生成一张图」「生成一段视频」「本周用了多少额度」变成 DSH 里的三个工具和一个输入框胶囊。

## 为什么是这个形态

网页自动化这条路有一个绕不开的事实：真正的会话在浏览器 profile 里。任何「导出 cookie 给服务端用」的方案都要把凭据搬一次家，而搬家就要落盘，落盘就要清理，清理就会漏。

所以这里换了一条：**让浏览器自己持有凭据，插件只驱动它**。具体表现为

- 每个账号一个浏览器数据目录 `profiles/<accountId>/`，与用户的日常 profile 彻底隔离；
- 插件从不读 cookie，账号索引里也不写；
- 登录是用户在**可见窗口**里自己完成的，插件的角色是事后用页面自己的 `/api/session` 确认结果。

代价是必须有一个真浏览器在线。这是有意的取舍：插件的前提里明写了 Chrome。

## 关键决定

### 一条发送路径，只扣一次扳机

`MusePage.sendOnce()` 是唯一的发送入口。它**先点按钮**，只有在完全没有可用按钮时才派发一次 Enter，并且**点过之后绝不再按 Enter**。

参考实现里有一个兜底：发出 25 秒后如果输入框还留着文字，就补点一次。这里删掉了。理由：那个兜底把「可能没发出去」变成「可能发出去两次」，而用户看不见第二次。本插件改成把不确定性交出来——25 秒给诊断，60 秒给「结果未知」，一次动作都没重复。

配套的是发送前先写日志：`state: possibly-sent` + `sendAttemptedAt` 落盘成功之后才允许动作。写盘失败就停止，不发。这样崩溃、断电、DSH 重启之后，任务记录仍然说得出「这一单可能已经出去了」，于是不重发。

### 页面同一时刻只跑一个任务

所有碰页面的动作都经过 `runExclusive`，包括额度读取、换号校验、对话测试。生成期间点设置卡里的按钮只会看到「忙碌」，不会把生成中的页面导航走。

队列用 promise 链而不是布尔标志：一个抛异常的操作用 `finally` 释放队列，异常不会把它永久卡死。

### 归因：只怪能证明的那一个

`lib/pool.js` 把失败分成六类，只有三类可以让当前账号退出本次任务：

- `signed-out`（会话检查明确 401 / 页面明确是登录墙）
- `quota-exhausted`（本轮助手输出里确认的周额度耗尽）
- `rate-limited`（上游自己的限流信号）

其余（断网、页面没就绪、浏览器崩了、看不懂的上游报错）都归 `shared`：本次尝试结束，但**不冷却任何账号**。故障前后两个账号的健康状态、冷却原因、`usableUntil` 必须一字不差——这是 A21 的判据。

「历史消息里提到额度」「用户的提示词里提到额度」都不构成冷却理由：识别函数的输入必须来自本轮助手输出。

### A16：发送之后，页面失联不是失败

发送动作一旦触发，请求就可能已经在上游。此时页面关闭、读取失败、等待超时，全部返回「结果未知」并把 `任务 · 账号 · 原因` 一起交出来，**不写 `FAILED`**。

这条规则贯穿三层：

1. `waitDelivery` 遇到页面关闭或读取失败时返回 `unknown: true` 加一个 `reason`，不抛共享故障；
2. 接单之后取媒体失败，日志一律落在 `UNKNOWN`，只有已核实的额度/限流例外（那条要冷却账号）；
3. 最外层的兜底 `catch` 只允许把 `queued`/`running` 写成 `FAILED`，绝不降级 `possibly-sent` 或 `accepted`。

写 `FAILED` 会让用户再发一次，而上游可能已经扣过费。三层缺任何一层，这个洞就还在。

### A15/A17：冷却停止任务，认证失效才换号

`eligibility()` 返回的 `maySwitch` 是这件事的唯一判据：

| 账号状态 | 可用 | 可以换成别的账号 | 理由 |
|---|---|---|---|
| 认证会话明确失效 | 否 | **是** | G5 表格唯一允许换号的情形（A15） |
| 本周额度耗尽 / 限流（冷却中） | 否 | **否** | 额度章节明写「本次任务停止」 |
| 冷却到期 | 否（需复核） | **否** | 恢复靠重新校验，不靠时钟 |
| 停用 | 否 | 否 | 不是认证问题，也不是额度问题 |
| 共享故障 | — | 否 | 不能把别人的额度花在同一个提示词上 |

早期版本把冷却归成 `signed-out`，于是下一次请求被提交到第二个账号——正是额度章节禁止的行为。

冷却到期只意味着**可以复核**：任务开始时先跑一次认证检查，通过才用。

### A17：重置时间与额度归因

- **只有具体时刻才算时刻。** 上游印的是 `Sep 30`——没有年份、没有时间、没有时区。把它换算成「Sep 30 00:00 UTC」等于凭空补出两个上游没说过的事实，而错的时间比没有时间更糟。只有带年份、日期、时间和明确时区的 ISO 串才被接受；其余保留原文并显示「恢复时间未知」。
- **只有本轮助手输出可以判额度。** 扫描范围是本轮基线之后新增的助手气泡，不是页面末尾。提示词里写了「weekly limit」、或者历史消息还挂在上面，都不会冷却账号——目标的原话是「用户提示词、历史消息或含义不明的 token limit 只作诊断」。页面尾部仍然会被收集，但只作为失败时的 `diagnosticTail` 给人看，不参与判定。

### 本轮归属

气泡总数不能说明哪条回复是本轮。`lib/probe.js` 的做法是：

1. 用**完整测试消息**精确匹配本轮用户气泡，且必须唯一；
2. 只读它之后、下一条用户消息之前的助手气泡；
3. 每次采样重新定位（Muse 会重绘，节点引用会过期）；
4. 角色、顺序、锚点任一不可辨 → 不判连通。

会话路径也是从**发送前**的路径取的，不是硬编码 `/thread/new`：Muse 在第一条消息落地时会把 `/thread/new` 改写成 `/thread/<id>`，硬编码会把每一次真实测试都判死。

### 完成判据

**计时从测试开始**，不是从页面就绪开始。G6 要求「从测试开始用单调时钟计时」，60 秒是整场测试的硬上限。因此账号校验和页面准备的时间也计入同一个预算——否则探针会白拿一段额外时间，而用户拿到的耗时也没法跟墙钟对上。

「单调」不是修辞：`Date.now()` 跟墙钟走，一次 NTP 校时就能把 60 秒的期限挪动几秒，要么凭空判超时，要么白送时间。这里用 `performance.now()`——相对任意原点的单调计数器。调用方把自己的起点传进来，于是校验、准备、轮询共用同一条时间线。

截止比较用 `>=`：正好落在截止点上的采样按超时算。目标的表格写的是「到达截止时优先记超时」，用 `>` 就是差一。

采样约 60 ms 一次。取得**非空正文且 Stop 未显示**时才知道「生成结束了」，以此刻全文为基线；随后连续 3 次采样同样满足才判完成。

Stop 一直显示时绝不建立基线——哪怕文字已经稳定几秒。正文变化、Stop 出现、读取失败、锚点丢失，全都清掉计数重来。

Stop 的判定是**看可见性**，不是看节点在不在：Muse 把 Stop 节点常挂，只切 display。只查 `querySelector` 会永远认为「还在生成」，于是每个测试都超时。

### 短码与三态

7 位、只含 `A-Z2-9`（去掉 O/0、I/1），形如 `MUSE-7K4P9D`。

- 全文与短码**完全相等** → 绿，`ok=true`
- 恰好出现一次短码且还有别的字 → 黄，`ok=true`，`note="助手未按约定格式回显"`
- 没出现、出现两次以上、或出现但回复没完成 → 等到 60 秒记超时，`ok=false`

匹配**区分大小写**：只回 `muse-7k4p9d` 按未回显处理，因为那是没照做。

60 秒是硬截止，优先级高于「短码出现了」：第 58 秒出现、Stop 撑到第 60 秒，就是超时，之后 Stop 消失也不改判。

### 媒体只认本轮的成品

`pickCandidate()` 排除两类东西：

- 发送前的基线里已经存在的源；
- 位于**用户气泡**内的附件（那是本轮上传的参考图，不是成品）。

参考实现用「上传字节的哈希」排除回显素材，这里先用结构（在不在用户气泡里）判，因为结构判定更便宜且不需要把字节读出来比对。取回后再按类型判一次：要视频就必须是视频，拿到图片就拒绝，绝不用封面充当成品。

### 窗口什么时候出现

**只有「打开登录窗口」会弹出窗口。** 这是设计决定，不是默认值凑巧如此：

| 动作 | 窗口 |
|---|---|
| 打开登录窗口 | **可见**——只有这里需要人坐在前面输入 |
| 文生图 / 文生视频 | 无头 |
| 对话测试 | 无头 |
| 额度读取（自动或手动） | 无头；浏览器没开就干脆不读 |

理由很直接：一次生成的结果出现在对话里，那才是用户在看的窗口；为它再开一个浏览器窗口只是打断，不带来任何信息。

额度读取更进一步：`readQuota` 接受 `allowLaunch`，后台定时器和设置卡的手动读取都传 `false`。**读一个数字不值得开一个浏览器**——没开就返回 `no-window`，胶囊保留上次的值并说明「下一次生成后自动更新」，这句话是真的。

### 额度胶囊：只显示，不操作

胶囊是读数，不是控件。

**它自己会更新**，不需要用户点任何东西：

1. 宿主按 `autoRefreshQuotaSeconds`（默认 300 秒）在后台刷新手选账号；
2. 每次生成**交付之后**立即再读一次——那一刻浏览器本来就开着，是成本最低、也最有意义的时机（显示的数字对应刚跑完的这一单）；
3. 任务占着页面时不发读取，避免和生成抢页面（A20）。

早期版本靠用户点胶囊上的 `↻` 才更新，这是个设计错误：把宿主自己能做的工作推给了用户，而且那个按钮背后的路由严格只认回环（A8），在这套只绑 LAN 地址的部署上直接 403。**手动刷新按钮已删除**，胶囊只负责显示，悬停时说明数字从哪来。

| 状态 | 什么时候 | 显示 |
|---|---|---|
| 有数字 | 读到值 | `已用 4%` |
| 转灰 | 上次成功、本次失败 | 保留旧数字，`stale: true` |
| 等待 | 还没有任何读数 | `待刷新`，悬停说明「下一次生成后自动更新」 |

页面被任务占用时，普通读取**只返回该账号的缓存**并注明时间。60 秒内的普通读取直接用缓存；强制读取绕缓存，但同一账号已有读取在途时复用它。

**胶囊读哪个账号**（G2/A4）：任务运行时读**任务实际在用的那个账号**——请求可能从手选账号起手，认证失效后切到备用账号，此时显示手选账号的余额就是在骗人（B 在扣费，A 在显示）。空闲时读手选账号，让用户看到的数字正是下一次请求会花的。

单账号不显示标签，多账号显示实际账号标签。

### 路由的访问范围

五条路由，**两道门依次通过**：先宿主，后插件自己。

**第一道：宿主鉴权。** 每条路由在读到任何请求数据之前，先调 DSH 的 `ctx.connection.requestRejection(req)`。这是 1.1.0 补上的——此前只有自建判据，任意网页都能调用这些接口，包括重置账号、清空媒体文件。检查在最前面，返回 401/403 就直接结束，请求体不读。

**第二道：插件自己的来源判据。** 宿主通过之后才轮到它，两组路由不同：

**额度路由 `/quota` —— 严格只认回环。** A8 的原文是「本机回环请求正常返回；非回环请求返回 403」，这里按字面实现：`Host` 必须指向回环、连接必须落在回环地址上、对端也必须是回环。

代价是明确的：这台机器上的部署只绑了 `192.168.1.3`、**没有 loopback 监听**，所以这条路由对所有请求都返回 403，包括本机浏览器。这是规格自己给出的答案，不是要绕过去的缺陷——**胶囊不依赖它**，胶囊读 `/accounts`。

**其余四条 —— 认「请求来自本机」。** 两个条件：`Host` 指向本机（回环，或连接实际落在的那个地址），且对端地址等于落地地址。第二个条件是关键：另一台机器访问同一个 LAN 监听时，内核报告的对端是它自己的地址，因此即使 `Host` 写得完全正确也会被拒。DNS rebinding 过不去，因为攻击页面的 `Host` 是它自己的域名，永远不等于落地地址。带 `Origin` 的写请求再核一次同源。

**两层是叠加，不是替换。** 宿主的检查拦住「没有 DSH 身份的调用者」，插件的检查拦住「有身份但不该从网页发起的请求」。单独任何一层都不够：只有宿主检查，则任何登录了 DSH 的页面都能改账号；只有本地检查，则同机其他进程可以冒充。

**缺 `requestRejection` 时，路由根本不会被注册。** `registerRoutes` 在开头就检查，拿不到这个函数直接返回——那些接口在这种宿主上不存在（404），而不是存在但放行。这是比「失败关闭」更彻底的一种：没有检查能力的实现里，这些能力干脆不出现。

这不是纯理论：`requestRejection` 首次出现在 `@deepseek-ai/dsh-client-connection` 0.1.2-alpha.2，而本插件声明的最低宿主是 0.2.2-rc.5，所以支持范围内不会缺少它。`SECURITY.md` 记录了这个下限。

## 已知限制

- **额度路由在只绑 LAN 地址的部署上仍只认回环。** 见上文「路由的访问范围」：该路由严格按 A8 的字面实现，因此在这种部署上对所有请求返回 403（包括本机浏览器）。胶囊改用 `/accounts`，不受影响。
- **网页结构依赖。** 选择器绑定在 Muse 当前的外壳上（`hatch-chat-groupable-bubble`、`hatch-agent-bubble-bg`、`chat-user-bubble`、`data-testid^=hatch-chat-attachment-presentation-`）。上游改版会让定位失败，此时插件报告**具体阶段**而不是猜一个结果。
- **首帧证据。** 插件会记录「本轮用户消息实际带了几个附件」，与交给输入框的文件数比对；但「上游确实把那张图当作起始画面」这一点只能在拿到成片后用播放器看，插件无法自证。A19 的第一帧核对仍需人工完成。
- **对话探测的 DOM 前提。** 角色、顺序、占位填字后的重定位都以 `/thread/new` 上的实页为准；未在真实页面上验证前，A13 的归属项保持待验。
- **额度面板文案。** 解析覆盖英文、繁体、简体三种写法；面板改文案会退化成「读不到」而不是误报一个百分比。
- **未实现**：代理中转、签到、媒体库、缩略图、FFmpeg、画布、批量工作台。

## 验证记录

本地在 Windows + Chrome 157（`C:\Program Files\Google\Chrome\Application\chrome.exe`）+ Node v24.22.3 上跑过：

- CDP 连接、页面 attach、`Runtime.evaluate`、`DOM.setFileInputFiles`、分块取字节；
- 标签页复用（重复与并发打开都落在同一个 tab）；
- 浏览器关闭后进程退出、profile 目录立刻可删；
- 对话探测的五条 A13 路径（精确、格式不符、小写、无回复、Stop 撑到截止），另有追加文字、迟到、占位重填三条；
- 送达与媒体：点一次按钮 → 出现新助手气泡 → 取回本轮成品，且不把上传的回显当成品；要视频时拒绝图片；
- A16 的三条：正常出图、无送达证据、输入框有残留；
- 路由门禁：loopback、LAN 同源、rebinding 域名、外部 Origin、缺失 Host。
